# Порт Skreen2Go на Windows

Документ описывает, из чего состоит задача, и фиксирует решение, которое нужно принять
до первой строки кода. Ничего из порта пока не написано — почему, сказано в конце.

## Что мы портируем на самом деле

Замер по текущему `main`:

| | |
|---|---|
| Всего строк (исходники + тесты) | 10 849 |
| Файлов в ядре | 20 |
| Из них зависят от Apple-фреймворков | 17 |
| Свободны от них полностью | 3 — `AnnotationSession.swift`, `Localization.swift`, `ScreenshotFileWriter.swift`, вместе 153 строки |

То есть переносится как есть примерно полтора процента кода. Это не пессимизм, а
устройство приложения: оно почти целиком состоит из работы с системой — захват экрана,
оверлей поверх рабочего стола, значок в строке меню, глобальная горячая клавиша, запись
видео. Ровно та часть, которая у каждой ОС своя.

Важно понимать, что это не «портирование» в смысле правки условной компиляции. Это вторая
реализация того же продукта, разделяющая с первой модель данных и арифметику.

## Чему на Windows нет прямой замены

| Сейчас | Windows | Насколько прямая замена |
|---|---|---|
| `SCScreenshotManager` — снимок области | Windows.Graphics.Capture, либо DXGI Desktop Duplication | Близко по смыслу, API совершенно другой |
| `SCStream` + `SCRecordingOutput` — запись в `.mp4` | Media Foundation Sink Writer, H.264 | Готового «пишущего выхода» нет: кадры и звук сводятся вручную |
| `SCContentFilter(excludingApplications:)` | `SetWindowDisplayAffinity(WDA_EXCLUDEFROMCAPTURE)` | Есть, но работает иначе: помечается наше окно, а не задаётся фильтр |
| `NSStatusItem` — значок в menu bar | `Shell_NotifyIcon` — область уведомлений | Похоже по роли, сильно отличается по поведению |
| Оверлей на уровне `.screenSaver` | Слоёное окно `WS_EX_LAYERED | WS_EX_TOPMOST` | Есть, но прозрачность и клики устроены иначе |
| `RegisterEventHotKey` (Carbon) | `RegisterHotKey` (Win32) | Прямая, самая простая часть всей задачи |
| `SMAppService` — запуск при входе | Ключ реестра `Run` или Task Scheduler | Прямая |
| `UserDefaults` | Реестр или свой файл настроек | Прямая |
| `AVCaptureDevice` — доступ к микрофону | WASAPI; разрешение через настройки приватности Windows | Модель разрешений другая |
| `NSVisualEffectView`, `CAGradientLayer`, `CIGaussianBlur` | Direct2D + DirectComposition | Переписывается целиком |
| Рисование аннотаций через `NSGraphicsContext` | Direct2D | Переписывается целиком |
| Security-scoped bookmarks | Не нужны — в Windows нет песочницы такого рода | Просто исчезает |
| `RiveRuntime.xcframework` | `rive-runtime` (C++, premake5, backend D3D11/D3D12) | Рантайм есть, но это другая сборка и другой язык |

Отдельно про анимацию руки: проверил — у Rive есть официальный C++ рантайм с бэкендами
D3D11 и D3D12, так что `hand.riv` проигрывается и на Windows. Но подключается он не
пакетом, а сборкой через premake5, и из Swift к нему придётся идти через C-обёртку.

## Что переносится без изменений

- `RecordingGeometry.swift` — выбор дисплея, `sourceRect`, приведение к чётным пикселям.
  Чистая арифметика, 198 строк, из Apple-фреймворков ей нужен только тип `CGRect`.
- Модель аннотаций и хранилище настроек из `Models.swift` — после замены `NSColor` на
  собственный тип цвета.
- `ScreenshotNaming` из `ImagePipeline.swift` — имена файлов и разрешение коллизий.
- Геометрия анимаций: `CaptureFlash.frame/center/alpha`, `HandFlourish.frame`.
- `AnnotationSession`, `Localization`, `ScreenshotFileWriter` — целиком.
- Тесты на всё перечисленное. Их около сорока, и они не трогают экран.

Это и есть настоящий первый шаг: вынести перечисленное в отдельный модуль, свободный от
AppKit, и убедиться, что macOS-версия на нём по-прежнему собирается и проходит тесты.
Такую работу можно проверить здесь и сейчас — в отличие от всего остального.

## Принятое решение: C# и .NET

Системный слой пишется на C#. Причина — родной доступ ко всему, что нужно: захват экрана
через WinRT, Media Foundation, область уведомлений, реестр. Всё документировано и обкатано,
в отличие от `swift-winrt`, который экспериментален.

Цена решения принимается сознательно: **общего кода с macOS-версией не остаётся**. Модель
аннотаций, арифметика геометрии, имена файлов и схема настроек переписываются на C#, и
тесты на них дублируются. Это примерно те самые полтора процента, что переносились бы
буквально, — потеря невелика, а выигрыш в зрелости платформенного слоя большой.

Конкретика стека:

- **.NET 9**, TFM `net9.0-windows10.0.26100.0` — нужен для вызова WinRT из C# через CsWinRT.
- **Оверлей выбора — не WPF.** У WPF прозрачность включается через `AllowsTransparency`,
  а он отключает аппаратное ускорение: полноэкранный оверлей на большом мониторе поедет
  программным рендерингом. Нужно слоёное окно Win32 плюс DirectComposition и Direct2D.
- **Окно настроек — WPF.** Здесь оно уместно: обычное окно, обычные контролы.
- **Трей** — `Shell_NotifyIcon` через P/Invoke.
- **Rive** — `rive-runtime`, собранный под D3D11, и тонкая C-обёртка для вызова из C#.

## План работ

Оценки — в рабочих днях одного опытного Windows-разработчика. Выведены из объёма
соответствующего кода на macOS и из того, насколько прямой оказалась замена API в таблице
выше. Это расчёт, а не замер: ни одна из фаз здесь не выполнялась.

### Фаза 0. Спайки — 3–5 дней

Сначала три вопроса, ответ «нет» на любой из которых меняет архитектуру. Тот же приём,
что применялся к записи видео на macOS: сперва проверить самое опасное, потом строить.

1. **Исключение своего окна из захвата.** `SetWindowDisplayAffinity` с
   `WDA_EXCLUDEFROMCAPTURE` должен убирать оверлей и панель из кадра Windows.Graphics.Capture.
   Если нет — рушится вся модель «панель поверх снимаемой области», и оверлей придётся
   гасить перед каждым кадром.
2. **Запись со звуком.** WGC отдаёт кадры, WASAPI — системный звук и микрофон, свести всё
   в один H.264 в `.mp4` должен Media Foundation Sink Writer. Прямого аналога
   `SCRecordingOutput`, который делает это сам, в Windows нет: синхронизация дорожек по
   общим часам — наша забота. Проверять на записи 10 секунд с обоими источниками.
3. **Rive под D3D11 из C#.** Собрать `rive-runtime` через premake5, написать C-обёртку,
   проиграть `hand.riv` в окне. Если не пойдёт — анимация руки становится опциональной,
   а не обязательной частью порта.

### Фаза 1. Общее ядро — 4–6 дней

Модель аннотаций, хранилище настроек (24 ключа), `RecordingGeometry`, `ScreenshotNaming`,
геометрия анимаций. Плюс перенос сорока существующих тестов — они не трогают экран и
переводятся почти механически. Отдельная работа — свой тип цвета вместо `NSColor`.

Фаза даёт проверяемый результат без единой строки UI и служит фундаментом для остального.

### Фаза 2. Оболочка — 5–7 дней

Значок в области уведомлений и меню, глобальная горячая клавиша через `RegisterHotKey`,
окно настроек на WPF, запуск при входе, локализация en/ru через `.resx`.

### Фаза 3. Захват — 5–8 дней

Снимок области и снимок окна, работа на нескольких мониторах, права доступа.

Здесь ждёт главная ловушка Windows, которой нет на macOS: **per-monitor DPI**. На macOS
координаты в точках, и разномасштабные мониторы система берёт на себя. В Windows
приложение объявляет себя `PerMonitorV2`-осведомлённым и пересчитывает координаты само,
иначе на смешанной конфигурации рамка выделения окажется не там, где курсор.

### Фаза 4. Оверлей и аннотации — 12–18 дней

Самая объёмная часть: на macOS это `Capture.swift` (2038 строк), `Editor.swift` (914) и
`ImagePipeline.swift` (395). Слоёное окно, рисование через Direct2D, панель действий,
палитра цветов, инструменты — стрелка с сужающимся хвостом, рамка, текст, размытие,
курсор, — выделение и перетаскивание объектов, Undo/Redo, полный редактор.

### Фаза 5. Запись — 10–15 дней

То, что подтвердил спайк, доведённое до продукта: машина состояний, обратный отсчёт,
источники звука, остановка из трея и клавишей, перенос готового файла, восстановление
после сбоя. Оценка велика потому, что сведение дорожек и обработка потери устройства —
именно та часть, где `SCRecordingOutput` на macOS делал работу за нас.

### Фаза 6. Мелочи, которые делают продукт — 5–8 дней

Тост-подтверждение, полёт снимка в трей, анимация руки, светящаяся рамка панели.

Отдельно: значок в трее пользователь может убрать в переполнение, и тогда у полёта нет
видимой цели. На macOS такого не бывает. Нужно поведение на этот случай.

### Фаза 7. Упаковка — 3–5 дней

MSIX, подпись кода, установщик. Плюс решение, идти ли в Microsoft Store или раздавать
самостоятельно, — от него зависит модель обновлений.

### Итого

**47–72 дня** одного разработчика на полной занятости, то есть примерно два с половиной —
три с половиной месяца. Фазы 4 и 5 вместе — почти половина всего объёма.

## Что решить до старта

- Минимальная версия Windows. От неё зависит доступность WGC-возможностей: исключение
  окна из захвата появилось в Windows 10 2004, и опираться на более ранние — значит
  писать запасной путь.
- Магазин или свой установщик. Меняет упаковку, подпись и обновления.
- Паритет с macOS-версией или своя дорога. Сейчас планируется полный паритет, но,
  например, полноценный редактор аннотаций — это половина фазы 4, и его можно отложить.

## Чего в этой ветке нет и почему

Кода порта здесь нет ни строки.

На этой машине его нельзя ни собрать, ни запустить: это macOS 26.6.2, .NET SDK и Windows
SDK отсутствуют. Написать десять тысяч строк, которые ни разу не проходили через
компилятор, — значит выдать за порт то, что портом не является: такой код выглядит
готовым, а на деле его отладка начнётся с нуля и займёт больше времени, чем написание с
чистого листа.

Поэтому здесь разбор задачи и план, а не имитация решения.
